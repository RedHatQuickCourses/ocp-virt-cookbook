= Hotplugging Volumes and Network Interfaces to Running VMs
:navtitle: Hotplug Volumes and Interfaces

== Overview

This tutorial demonstrates how to dynamically add and remove storage volumes to running virtual machines without requiring a restart. Hotplugging enables zero-downtime storage expansion, flexible resource allocation, and reduced maintenance windows.

You will use `virtctl addvolume` to attach a new PVC to a running VM, verify it appears as a new block device inside the guest, and then remove it with `virtctl removevolume`. The network interface section explains its cluster prerequisites and prepares a one-interface VM and secondary network for a later hotplug exercise.

== When to Use Hotplugging

Hotplugging is useful whenever storage or network needs change after a VM is already serving traffic, and a restart would be disruptive:

* **Database growth**: A production database VM is running out of disk space. Attach an additional storage volume without downtime.
* **Debug and diagnostic volumes**: Attach a scratch volume to a running production VM, collect logs or a memory dump, then detach it. No restart, and the VM keeps serving requests.
* **Dynamic network segments**: An application VM needs access to a new VLAN. Hotplug a secondary network interface instead of restarting the VM.
* **Temporary scratch storage**: Attach extra storage for a batch job, then remove it when the job completes, so the capacity is not tied up permanently.
* **Compliance data collection**: Attach an audit volume, collect the required data, and detach it, keeping the window in which the storage is attached as short as possible.

TIP: The use case determines whether you want the `--persist` flag. Long-lived data disks should be persisted so they survive a restart; temporary volumes for diagnostics, batch jobs, or audits are usually attached without it. See <<persist-flag>>.

== How Hotplugging Works

Hotplugging changes the VM's device layout while the VM keeps running. The base VM in this tutorial boots with two virtio disks; adding a volume introduces a third device without interrupting the VM:

....
BEFORE  — hotplug-vm running
│
├─ rootdisk        — vda   (virtio)
└─ cloudinitdisk   — vdb   (virtio)

   virtctl addvolume hotplug-vm --volume-name=hotplug-disk --persist
   the VM keeps running — no restart, no downtime

AFTER   — the same hotplug-vm, still running
│
├─ rootdisk        — vda   (virtio)
├─ cloudinitdisk   — vdb   (virtio)
└─ hotplug-disk    — sda   (SCSI, hotplugged)
....

Note that the hotplugged volume appears as `sda`, not `vdc`. Hotplugged volumes are attached to the SCSI bus rather than the virtio PCI bus, because virtio disks cannot be added to the PCI bus after boot. This is why the device name changes prefix. See <<disk-bus-type>> for details.

Behind that single `virtctl` command, the PVC reaches the guest through an attachment pod:

....
PersistentVolumeClaim (hotplug-disk)
│
└─ virtctl addvolume  — patches the running VM
   │
   └─ attachment pod  — makes the PVC available to the VM's launcher pod
      │
      └─ /dev/sda in the guest  — a new block device, ready to format
....

The attachment pod is visible in the VMI status as the `hotplugVolume` field, which you will see in Step 4.

== Step 1: Create a Namespace and Base VM

Create a namespace and deploy a VM to use as the hotplug target.

[source,bash,role=execute]
----
oc create namespace hotplug-demo
----

WARNING: The cloud-init password in this example is for demo purposes only. Always use a strong, unique password or SSH key authentication in production environments.

xref:attachment$hotplug-volumes-interfaces/vm-hotplug.yaml[Download vm-hotplug.yaml]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: hotplug-vm
  namespace: hotplug-demo
spec:
  runStrategy: Always
  template:
    metadata:
      labels:
        kubevirt.io/domain: hotplug-vm
    spec:
      domain:
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
          interfaces:
          - name: default
            masquerade: {}
        resources:
          requests:
            memory: 1Gi
      networks:
      - name: default
        pod: {}
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:latest
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            user: fedora
            password: fedora
            chpasswd:
              expire: false
EOF
----

Wait for the VM to start:

[source,bash,role=execute]
----
oc get vm -n hotplug-demo -w
----

Once `STATUS=Running` and `READY=True`, proceed. Press `Ctrl+C` to exit the watch.

Verify the initial disk layout:

[source,bash,role=execute]
----
oc get vmi hotplug-vm -n hotplug-demo -o jsonpath='{range .status.volumeStatus[*]}{.name}: {.target}{"\n"}{end}'
----

Expected output:
[source,text]
----
rootdisk: vda
cloudinitdisk: vdb
----

== Step 2: Create a PVC for Hotplugging

Create a PersistentVolumeClaim that will be hotplugged into the running VM.

xref:attachment$hotplug-volumes-interfaces/hotplug-pvc.yaml[Download hotplug-pvc.yaml]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: hotplug-disk
  namespace: hotplug-demo
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: lvms-vg1
  volumeMode: Block
EOF
----

IMPORTANT: Hotplug volumes must use `volumeMode: Block`. Filesystem-mode PVCs require a pre-created `disk.img` file and are not suitable for direct hotplug of blank volumes.

Wait for the PVC to be provisioned. With `WaitForFirstConsumer` binding mode, it may remain `Pending` until attached:

[source,bash,role=execute]
----
oc get pvc hotplug-disk -n hotplug-demo
----

== Step 3: Hotplug the Volume

Use `virtctl addvolume` to attach the PVC to the running VM:

[source,bash,role=execute]
----
virtctl addvolume hotplug-vm --volume-name=hotplug-disk --namespace=hotplug-demo --persist
----

Expected output:
[source,text]
----
Successfully submitted addvolume request to VM hotplug-vm for volume hotplug-disk
----

The `--persist` flag ensures the volume remains attached after VM restarts. Without it, the volume would be detached on the next reboot.

== Step 4: Verify the Hotplugged Volume

Check the VMI volume status to confirm the new disk appeared:

[source,bash,role=execute]
----
oc get vmi hotplug-vm -n hotplug-demo -o jsonpath='{range .status.volumeStatus[*]}{.name}: {.target} (hotplugVolume: {.hotplugVolume}){"\n"}{end}'
----

Expected output:
[source,text]
----
rootdisk: vda (hotplugVolume: )
cloudinitdisk: vdb (hotplugVolume: )
hotplug-disk: sda (hotplugVolume: {"attachPodName":"...","attachPodUID":"..."})
----

The hotplugged volume appears as a SCSI device (`sda`) with phase `Ready`. Note the `hotplugVolume` field with attach pod information.

Verify the PVC is now bound:

[source,bash,role=execute]
----
oc get pvc hotplug-disk -n hotplug-demo
----

Expected output:
[source,text]
----
NAME           STATUS   VOLUME       CAPACITY   ACCESS MODES   STORAGECLASS   AGE
hotplug-disk   Bound    pvc-xxxx     5Gi        RWO            lvms-vg1       1m
----

Verify from inside the guest. Access the VM console:

[source,bash,role=execute]
----
virtctl console hotplug-vm -n hotplug-demo
----

Log in with username `fedora` and password `fedora`, then list block devices:

[source,bash]
----
lsblk
----

You should see a new disk device (e.g., `sda`) with the size matching the PVC. Press `Ctrl+]` to exit.

== Step 5: Format and Use the Hotplugged Disk (Inside the Guest)

Inside the VM console, format the new disk:

[source,bash]
----
sudo mkfs.xfs /dev/sda
----

Create a mount point and mount the disk:

[source,bash]
----
sudo mkdir -p /mnt/hotplug
sudo mount /dev/sda /mnt/hotplug
----

Write a test file and verify:

[source,bash]
----
echo "Hotplug test" | sudo tee /mnt/hotplug/test.txt
----

[source,bash]
----
cat /mnt/hotplug/test.txt
----

Expected output:
[source,text]
----
Hotplug test
----

Unmount before removing:

[source,bash]
----
sudo umount /mnt/hotplug
----

Press `Ctrl+]` to exit the console.

== Step 6: Remove the Hotplugged Volume

Detach the volume from the running VM:

[source,bash,role=execute]
----
virtctl removevolume hotplug-vm --volume-name=hotplug-disk --namespace=hotplug-demo
----

Expected output:
[source,text]
----
Successfully submitted removevolume request to VM hotplug-vm for volume hotplug-disk
----

IMPORTANT: Always unmount the filesystem inside the guest before removing a hotplugged volume to prevent data corruption.

Verify the volume was removed:

[source,bash,role=execute]
----
oc get vmi hotplug-vm -n hotplug-demo -o jsonpath='{range .status.volumeStatus[*]}{.name}: {.target}{"\n"}{end}'
----

Expected output:
[source,text]
----
rootdisk: vda
cloudinitdisk: vdb
----

The hotplug-disk is no longer attached. The PVC still exists and retains the data:

[source,bash,role=execute]
----
oc get pvc hotplug-disk -n hotplug-demo
----

== Hotplug Volume Reference

[#persist-flag]
=== The --persist Flag

[cols="1,1",options="header"]
|===
| Flag
| Behavior

| `--persist`
| Volume is added to the VM spec and survives restarts

| (no flag)
| Volume is attached only to the current VMI; lost on restart
|===

Use `--persist` for data disks that should remain attached permanently. Omit it for temporary operations like data migration or one-time imports.

=== Supported Volume Types

Hotplug supports:

* PersistentVolumeClaims (PVCs)
* DataVolumes

Hotplug does not support:

* containerDisk volumes
* cloudInitNoCloud / cloudInitConfigDrive volumes
* emptyDir volumes

[#disk-bus-type]
=== Disk Bus Type

Hotplugged volumes use the SCSI bus by default (appearing as `sda`, `sdb`, etc.), unlike virtio disks which appear as `vda`, `vdb`. This is because virtio disks cannot be hotplugged to the PCI bus after boot. SCSI provides hot-add capability.

== Network Interface Hotplugging

OpenShift Virtualization supports hotplugging network interfaces through two paths:

|===
| Path | How the interface is added | Migration | Support level

| Migration-based hotplug
| Live migration creates a destination virt-launcher pod with the new interface, then attaches it to the running guest.
| Required; automatic on OpenShift 4.20+ with `LiveUpdate`, manual on 4.18/4.19
| Supported by Red Hat

| In-place hotplug
| OpenShift's thick Multus plugin and the upstream Multus Dynamic Networks Controller (DNC) add the interface to the existing virt-launcher pod and running guest.
| Not required
| Upstream DNC; not shipped or supported by Red Hat
|===

NOTE: `LiveMigratable` is a VMI condition shown in the web console. `LiveUpdate` is the VM rollout-strategy value that enables automatic migration for VM changes on OpenShift 4.20 and later. They are related but are not interchangeable.

This section focuses on hotplugging and unplugging a network interface and verifying whether it was attached in place or through migration. For the complete secondary-network setup and connectivity verification, see xref:networking:linux-bridges.adoc[Linux Bridges].

The result is the same pattern as volume hotplugging, the running VM gains a device it did not boot with:

....
BEFORE  — one interface
│
└─ default     — masquerade, pod network

   edit the VM spec to add an interface backed by a NAD

AFTER   — two interfaces
│
├─ default     — masquerade, pod network
└─ dyniface1   — bridge, secondary network
....

=== How It Works

Unlike volume hotplugging (which uses `virtctl addvolume`), network interface hotplugging is done by patching the VM spec:

. Create a NetworkAttachmentDefinition (NAD) for the secondary network.
. Patch the VM spec to add the new interface and network definitions.
. In-place hotplug adds the interface to the existing launcher pod and guest through thick Multus and the DNC. Migration-based hotplug creates a destination launcher pod with the attachment and adds the guest interface when live migration completes. Both paths update the running VM without a stop/start cycle.

image::nic-hotplug-flow.svg[NIC hotplug and unplug flow, align=center]

KubeVirt uses the launcher's `k8s.v1.cni.cncf.io/network-status` annotation to determine whether the requested pod attachment is present. A working DNC can provide that attachment in place. If it is not present, completion requires the migration-based path: automatic with `LiveUpdate` on OpenShift 4.20+, or manually triggered on 4.18/4.19. Verify the actual outcome using the VMI’s `status.nodeName` and `status.migrationState`, the pod `network-status` annotation, and the migration records rather than inferring it from the installed components alone.

=== Prerequisites

*Common requirements*

* *OpenShift {ocp-min-version}+* with OpenShift Virtualization installed.
* *Cluster-admin access* (`system:admin` or equivalent) for this tutorial's cluster configuration and migration operations.
* *The `oc` and `virtctl` CLI tools*: `virtctl` is needed for manual migration on OpenShift 4.18 and 4.19.
* *Secondary network*: A NetworkAttachmentDefinition (NAD) must refer to a bridge already configured on every node where the VM can run.

*Path 1: Migration-based hotplug*

* *`LiveUpdate` VM rollout strategy*: On OpenShift 4.20 and later, hotplug and unplug changes trigger live migration automatically. On OpenShift 4.18 and 4.19, the VMI picks up the change, but you must trigger migration manually with `virtctl migrate` after the change reaches the VMI.
* *At least two schedulable workers* that meet the VM's placement and resource requirements.
* *A live-migratable VM*: PVC-backed disks require migration-compatible shared RWX storage. The ContainerDisk baseline in this example is suitable for the demonstration.

*Path 2: In-place hotplug*

* *Thick Multus CNI plugin*: Included by default in the OpenShift versions supported by this tutorial.
* *Multus Dynamic Networks Controller (DNC)*: An upstream, Red Hat-unsupported controller that watches network attachment changes and asks Multus to configure attachments on existing pods. A ready DNC pod must run on every node where the VM can run; each controller handles only pods on its own node.

In-place hotplug does not require migration, so it can work on a single worker and with RWO-backed VM disks.

NOTE: If you plan to try both paths, complete Path 1 before installing the DNC in Path 2. A DNC already serving the VM's node changes the observed result to in-place behavior.

SR-IOV hotplug always uses migration, even when the DNC is installed. This example uses bridge binding.

NOTE: The KubeVirt version included with OpenShift Virtualization can change between OpenShift releases. Use the OpenShift-version-specific capabilities described here rather than assuming the underlying KubeVirt version stays the same across releases.

<.> Use bridge binding for the hotplugged interface.
<.> Add a matching network entry with the same interface name.

What happens next depends on your OpenShift Virtualization release:

==== Step 5: Verify the Migration-Based Hotplug

Live migration creates a new virt-launcher pod with the updated interface spec, migrates the running guest to it, and keeps the same VMI object. The VMI name does not change; the node it runs on does. Follow these checks in order to see each layer of the result. They confirm hotplug, not network connectivity.

. Confirm the migration object succeeded:
+
[source,bash,role=execute]
----
oc get vmim -n "$NAMESPACE"
----
+
Look for a migration with `Succeeded`.

. Inspect the launcher pods for this VM:
+
[source,bash,role=execute]
----
oc get pods -n "$NAMESPACE" -l kubevirt.io/domain="$MIG_VMI_NAME" -o wide
----
+
During migration you may see both the old and new virt-launcher pods:
+

INPLACE_DNC_POD=$(oc get pods -A -l name=dynamic-networks-controller --field-selector="spec.nodeName=$INPLACE_NODE_BEFORE" -o jsonpath='{.items[0].metadata.name}')
if [ -z "$INPLACE_DNC_POD" ]; then
  printf 'No DNC pod found on node %s\n' "$INPLACE_NODE_BEFORE" >&2
else
  printf 'DNC pod: %s/%s\n' "$INPLACE_DNC_NAMESPACE" "$INPLACE_DNC_POD"
  oc get pod "$INPLACE_DNC_POD" -n "$INPLACE_DNC_NAMESPACE" -o wide
fi
----

Expected output:
[source,text]
----
DNC pod: hotplug-demo/dynamic-networks-controller-ds-cp78b
NAME                                   READY   STATUS    RESTARTS   AGE   IP            NODE                          NOMINATED NODE   READINESS GATES
dynamic-networks-controller-ds-cp78b   1/1     Running   0          5m    10.129.0.7    ip-10-0-74-246.ec2.internal   <none>           <none>
----

The `NODE` column matches the baseline node recorded in Step 3, confirming this is the controller responsible for the VM's launcher pod.

Then print the lines from that DNC pod's logs that relate to the removal:

[source,bash,role=execute]
----
oc logs -n "$INPLACE_DNC_NAMESPACE" "$INPLACE_DNC_POD" -c dynamic-networks-controller --timestamps=true | grep -i 'remove'
----

The exact log wording varies by DNC version, so there is no fixed expected output. Look for timestamped lines near the time of the unplug patch that reference the removal of the `hotplug-demo/lnbr0-bridge` attachment from the `virt-launcher-nic-hotplug-inplace-<hash>` pod. The `--timestamps` flag makes it easier to correlate the log lines with the unplug. If nothing matches, widen the pattern, for example `grep -iE 'remov|lnbr0|nic-hotplug'`, or view the full logs without the filter.

NOTE: DNC logs provide evidence of the pod-side attachment removal only; KubeVirt handles the guest-side NIC detach. An empty `grep` result does not by itself prove the removal failed. Confirm the end result with the checks below.

Repeat the launcher pod, `network-status`, VMI mapping, and guest `ip -br link` checks to verify that the interface has been unplugged. The requested networks annotation drives the DNC; `network-status` reports the resulting attachments.

=== Troubleshooting Network Hotplug

*Migration-based path*

* *"Pending changes"*: Inspect `MigrationRequired` and `LiveMigratable` in the VMI conditions. A tested blocked case reported `MigrationRequired=True` with reason `AutoMigrationDueToLiveUpdate` and `LiveMigratable=False`. Check the condition message for the migration blocker. A single worker or non-migratable RWO disks can prevent the migration-based path from completing.
* *VMI spec updated, but no guest NIC*: Check `network-status` on the current launcher pod. If the attachment is absent, the DNC has not attached it in place. For migration-based hotplug on 4.18/4.19, trigger manual migration after the change reaches the VMI. On 4.20+, verify the VM rollout strategy is `LiveUpdate`, check the VMI's `LiveMigratable` condition in the web console, and inspect migration progress. Confirm placement and shared-storage requirements.
* *Automatic migration does not start on OpenShift 4.20 or later*: Check the effective VM rollout strategy. `LiveUpdate` is required for automatic migration-based hotplug. The HyperConverged operator manages the rollout strategy and reconciles it to `LiveUpdate`; do not edit the KubeVirt custom resource directly. Ask the cluster administrator to inspect HyperConverged conditions and operator logs. The upstream rollout-strategy guide explains behavior, but its KubeVirt custom-resource editing procedure does not apply to OpenShift.

+
[source,bash,role=execute]
----
oc get kubevirt -n openshift-cnv -o jsonpath='{.items[0].spec.configuration.vmRolloutStrategy}{"\n"}'
oc get hyperconverged kubevirt-hyperconverged -n openshift-cnv -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
----

* *Migration cannot find an eligible target*: The migration-based path needs at least two schedulable workers that are Ready, meet the VM's placement and resource requirements, and have the secondary network configured. If a migration remains pending or fails, inspect worker readiness and taints:

+
[source,bash,role=execute]
----
oc get nodes -l node-role.kubernetes.io/worker --field-selector=spec.unschedulable=false -o wide
oc get nodes -l node-role.kubernetes.io/worker --field-selector=spec.unschedulable=false -o jsonpath='{range .items[*]}{.metadata.name}{" taints="}{.spec.taints}{"\n"}{end}'
----

+
Worker count alone does not establish migration readiness; available capacity, placement constraints, and network configuration on eligible nodes also matter.

*In-place path*

* *DNC works on only some VMs*: Compare the VM's node with the DNC pod list. Each controller serves only its own node; it must be ready on every VM-eligible node.
* *DNC pods rejected or not Ready*: Check DaemonSet events, the privileged SCC RoleBinding, namespace Pod Security labels, image pull errors, and host socket availability.

For the demo DNC, inspect events and logs with:

[source,bash,role=execute]
----
oc describe daemonset dynamic-networks-controller-ds -n "$NAMESPACE"
oc get pods -n "$NAMESPACE" -l name=dynamic-networks-controller -o wide
oc logs <dnc-pod> -n "$NAMESPACE"
----

== Cleanup

Remove the demo namespace:

[source,bash,role=execute]
----
oc delete namespace "$NAMESPACE"
----

Deleting the namespace removes its namespaced resources, including both demo VMs, the demo DNC DaemonSet, ServiceAccount, ConfigMap, and SCC RoleBinding.

Only if you installed the DNC for this demo, remove its ClusterRole and ClusterRoleBinding, which namespace deletion does not remove. Skip this command for the migration-only path or when using a preexisting cluster-infrastructure DNC deployment:

[source,bash,role=execute]
----
oc delete clusterrole,clusterrolebinding dynamic-networks-controller
----

This cleanup removes the demo DNC from the cluster; it no longer serves pods in other namespaces. Namespace deletion also removes resources created by the storage tutorial in `hotplug-demo`.

== Summary

In this tutorial you learned how to:

* Recognize the scenarios where hotplugging avoids a disruptive restart
* Trace how a PVC reaches the guest as a new block device, and why it appears on the SCSI bus
* Hotplug a PVC volume to a running VM using `virtctl addvolume`
* Use the `--persist` flag to make hotplugged volumes survive restarts
* Verify hotplugged volumes appear as new block devices inside the guest
* Format and mount hotplugged storage within the VM
* Remove hotplugged volumes with `virtctl removevolume`
* Compare the in-place (upstream DNC) and supported migration-based network hotplug paths
* Check path-specific prerequisites and prepare a one-interface VM baseline for each path
* Verify network interface hotplug and unplug using the VMI node and migration state, launcher pod `network-status`, and guest device checks
* Use automatic migration on OpenShift 4.20+ or manual migration on 4.18/4.19 for the migration-based path
* Request bridge-interface unplug with `state: absent` and remove the demo DNC during cleanup
