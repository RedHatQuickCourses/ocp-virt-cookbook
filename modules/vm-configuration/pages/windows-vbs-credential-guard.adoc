= Enabling Virtualization-Based Security for Windows VMs
:navtitle: Windows VBS and Credential Guard

== Overview

Virtualization-Based Security (VBS) is a Windows feature that uses a hypervisor to isolate a region of memory, called Virtual Trust Level 1 (VTL1), from the running Windows kernel in VTL0. Code and secrets placed in VTL1 stay unreadable to anything in the normal kernel, including kernel-mode malware. Two services build on that isolation:

* **Credential Guard** moves the LSA secrets process into VTL1 as `LsaIso.exe`. NTLM hashes and Kerberos ticket-granting tickets never appear in LSASS memory, so credential dumping tools have nothing to read.
* **Hypervisor-Protected Code Integrity (HVCI)**, shown as *Memory integrity* in the Windows Security app, performs kernel code-integrity checks inside VTL1. A kernel page becomes executable only after the secure kernel validates its signature, which blocks unsigned drivers and kernel-mode code injection.

Windows 11 enables VBS and HVCI by default on capable hardware, and Microsoft Secured-core Server baselines require both. Windows Server 2022 supports VBS but leaves it off until you enable it.

On OpenShift Virtualization the VBS hypervisor runs inside the Windows guest, on top of KVM on the node. VBS is therefore a nested virtualization workload, and the VM needs a specific hardware profile: nested virtualization CPU extensions, UEFI Secure Boot with SMM, a vTPM, and Hyper-V enlightenments.

WARNING: Nested virtualization is not supported for production workloads on OpenShift Virtualization. Use this configuration for development, testing, and security validation.

== How VBS Maps to the VM Configuration

....
  Windows guest
  +----------------------------------+  +---------------------------------+
  |  VTL0 (normal world)             |  |  VTL1 (secure world)            |
  |  Applications                    |  |  LsaIso.exe (Credential Guard)  |
  |  Windows kernel and drivers      |  |  Secure kernel + HVCI checks    |
  +----------------+-----------------+  +----------------+----------------+
                   |                                     |
                   +------------------+------------------+
                                      |
              +-----------------------------------------------+
              |  Hyper-V hypervisor inside the guest          |
              |  requires vmx (Intel) or svm (AMD) in the VM  |
              +-----------------------+-----------------------+
                                      |
              +-----------------------------------------------+
              |  virt-launcher pod: QEMU + KVM                |
              |  OVMF Secure Boot | SMM | vTPM 2.0            |
              +-----------------------+-----------------------+
                                      |
              +-----------------------------------------------+
              |  RHCOS node: KVM with nested = Y              |
              |  Intel VT-x + EPT  or  AMD-V + NPT            |
              +-----------------------------------------------+
....

Each Windows requirement maps to one field in the VM spec:

[cols="1,2,2",options="header"]
|===
|Windows requirement |VM spec field |Purpose

|Hypervisor support
|`domain.cpu.features` with `vmx` or `svm`
|Lets the Hyper-V hypervisor start inside the guest

|UEFI firmware
|`domain.firmware.bootloader.efi`
|VBS requires UEFI, not SeaBIOS

|Secure Boot
|`domain.firmware.bootloader.efi.secureBoot`
|Required platform security feature for VBS

|SMM
|`domain.features.smm.enabled`
|Secure Boot variables are protected by System Management Mode

|Persistent firmware state
|`domain.firmware.bootloader.efi.persistent`
|Keeps Secure Boot variables across reboots

|TPM 2.0
|`domain.devices.tpm.persistent`
|Stores Credential Guard and BitLocker keys across reboots

|Hyper-V enlightenments
|`domain.features.hyperv`
|Synthetic timers, synic, IPI, and TLB flush support the guest hypervisor
|===

== Prerequisites

* OpenShift {ocp-min-version}+ with the OpenShift Virtualization operator installed
* Cluster admin access, required to read node labels and patch the `HyperConverged` custom resource
* `oc` and `virtctl` CLIs installed and configured
* Nodes with Intel VT-x plus EPT, or AMD-V plus NPT, enabled in the node firmware
* Nested virtualization enabled on the nodes that will run the VM, see xref:performance:nested-virtualization.adoc[Enabling Nested Virtualization for Development and Testing]
* A Windows Server 2022 boot source, such as the `win2k22` DataSource in the `openshift-virtualization-os-images` namespace or a golden image you built with xref:vm-lifecycle:windows-golden-images.adoc[Creating Windows Golden Images]
* A storage class with at least 100 Gi free for the VM disk and the VM state volume
* Administrator credentials for the Windows guest

== Step 1: Verify Node Support

The KubeVirt node labeller adds a `cpu-feature.node.kubevirt.io/vmx` label to Intel nodes that expose the nested virtualization extension, and `cpu-feature.node.kubevirt.io/svm` on AMD nodes. List the nodes that carry the Intel label:

[source,bash,role=execute]
----
oc get nodes -l cpu-feature.node.kubevirt.io/vmx
----

.Expected output
[source,text]
----
NAME       STATUS   ROLES                         AGE   VERSION
ocplab01   Ready    control-plane,master,worker   88d   v1.35.5
----

On AMD nodes, run the same command with the `svm` label:

[source,bash,role=execute]
----
oc get nodes -l cpu-feature.node.kubevirt.io/svm
----

If neither command returns a node, nested virtualization is off. Confirm at the kernel level and then enable it:

[source,bash,role=execute]
----
oc debug node/<node-name> -q -- chroot /host cat /sys/module/kvm_intel/parameters/nested
----

.Expected output
[source,text]
----
Y
----

An `N` means the `kvm_intel` or `kvm_amd` module was loaded without nesting. Follow xref:performance:nested-virtualization.adoc[Enabling Nested Virtualization for Development and Testing] before continuing.

Check the installed OpenShift Virtualization version. Persistent vTPM and persistent UEFI state require 4.14 or later:

[source,bash,role=execute]
----
oc get csv -n openshift-cnv -o custom-columns=NAME:.metadata.name,VERSION:.spec.version,PHASE:.status.phase
----

.Expected output
[source,text]
----
NAME                                       VERSION   PHASE
kubevirt-hyperconverged-operator.v4.22.9   4.22.9    Succeeded
----

== Step 2: Configure Storage for Persistent VM State

A vTPM keeps Credential Guard keys only if its contents survive reboots. KubeVirt stores vTPM contents and UEFI variables in a per-VM state PVC, and it creates that PVC from the storage class named in `spec.storage.vmStateStorageClass` of the `HyperConverged` custom resource.

Read the current value:

[source,bash,role=execute]
----
oc get hco -n openshift-cnv kubevirt-hyperconverged -o jsonpath='{.spec.storage.vmStateStorageClass}{"\n"}'
----

An empty result means no state storage class is set, and any VM that requests `persistent: true` fails to start. List the available storage classes:

[source,bash,role=execute]
----
oc get storageclass
----

Patch the `HyperConverged` custom resource with the storage class you want to use:

[source,bash,role=execute]
----
oc patch hco -n openshift-cnv kubevirt-hyperconverged --type=merge \
  -p '{"spec":{"storage":{"vmStateStorageClass":"nfs-storage"}}}'
----

NOTE: Choose a storage class that supports the `ReadWriteMany` access mode if you plan to migrate other VMs that use persistent state. The VM in this tutorial cannot live migrate in any case, because nested virtualization pins it to its node.

Confirm the value was accepted:

[source,bash,role=execute]
----
oc get hco -n openshift-cnv kubevirt-hyperconverged -o jsonpath='{.spec.storage.vmStateStorageClass}{"\n"}'
----

.Expected output
[source,text]
----
nfs-storage
----

== Step 3: Create the Windows VM

Create a namespace for the VM:

[source,bash,role=execute]
----
oc new-project windows-vbs
----

The manifest below defines every VBS requirement explicitly instead of relying on the `windows.2k22.virtio` preference, so you can see which field does what. The `vmx` CPU feature with `policy: require` adds a node selector for the nested virtualization label, which keeps the VM on a capable node.

xref:attachment$windows-vbs-credential-guard/win2k22-vbs-vm.yaml[Download win2k22-vbs-vm.yaml]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: win2k22-vbs
  namespace: windows-vbs
spec:
  runStrategy: RerunOnFailure
  dataVolumeTemplates:
    - metadata:
        name: win2k22-vbs-rootdisk
      spec:
        sourceRef:
          kind: DataSource
          name: win2k22
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 80Gi
  template:
    metadata:
      labels:
        kubevirt.io/domain: win2k22-vbs
    spec:
      evictionStrategy: None
      terminationGracePeriodSeconds: 3600
      domain:
        cpu:
          sockets: 1
          cores: 4
          threads: 1
          model: host-passthrough
          features:
            - name: vmx
              policy: require
        memory:
          guest: 8Gi
        firmware:
          bootloader:
            efi:
              secureBoot: true
              persistent: true
        features:
          acpi:
            enabled: true
          apic:
            enabled: true
          smm:
            enabled: true
          hyperv:
            relaxed:
              enabled: true
            vapic:
              enabled: true
            vpindex:
              enabled: true
            runtime:
              enabled: true
            synic:
              enabled: true
            synictimer:
              enabled: true
              direct:
                enabled: true
            frequencies:
              enabled: true
            reenlightenment:
              enabled: true
            ipi:
              enabled: true
            tlbflush:
              enabled: true
            reset:
              enabled: true
            spinlocks:
              spinlocks: 8191
        clock:
          utc: {}
          timer:
            hpet:
              present: false
            hyperv: {}
            pit:
              tickPolicy: delay
            rtc:
              tickPolicy: catchup
        devices:
          tpm:
            persistent: true
          disks:
            - name: rootdisk
              bootOrder: 1
              disk:
                bus: virtio
          interfaces:
            - name: default
              masquerade: {}
              model: virtio
          inputs:
            - name: tablet
              type: tablet
              bus: usb
      networks:
        - name: default
          pod: {}
      volumes:
        - name: rootdisk
          dataVolume:
            name: win2k22-vbs-rootdisk
EOF
----

IMPORTANT: Use `host-passthrough` or `host-model` for `domain.cpu.model`. A named CPU model such as `Haswell-noTSX` does not carry the `vmx-*` sub-features that the guest hypervisor needs, and VBS stays inactive even when the `vmx` flag is present.

NOTE: Leave `hyperv.evmcs` unset. Enlightened VMCS is an optimization for a guest hypervisor, and it interferes with nested VBS on several host kernel versions. The Red Hat `windows.2k22.virtio` preference also leaves it off.

Wait for the disk import and the first boot:

[source,bash,role=execute]
----
oc get vm win2k22-vbs -n windows-vbs -w
----

.Expected output
[source,text]
----
NAME          AGE   STATUS    READY
win2k22-vbs   6m    Running   True
----

Press `Ctrl+C` when the status shows `Running`.

== Step 4: Verify the Virtual Hardware

Before touching the guest, confirm that QEMU received the requested hardware. Find the `virt-launcher` pod:

[source,bash,role=execute]
----
oc get pod -n windows-vbs -l vm.kubevirt.io/name=win2k22-vbs
----

Dump the domain XML from the `compute` container. The libvirt domain is named `<namespace>_<vm-name>`:

[source,bash,role=execute]
----
POD=$(oc get pod -n windows-vbs -l vm.kubevirt.io/name=win2k22-vbs -o name)
oc exec -n windows-vbs $POD -c compute -- virsh dumpxml windows-vbs_win2k22-vbs
----

Check for these elements in the output:

* `<smm state='on'/>` inside `<features>`
* `<loader ... secure='yes'>` and `<nvram ...>` inside `<os>`
* `<feature policy='require' name='vmx'/>` inside `<cpu>`
* `<tpm model='tpm-crb'>` with `<backend type='emulator' version='2.0' persistent_state='yes'/>`
* The `<hyperv>` block with `synic`, `stimer`, `ipi`, `tlbflush`, and `frequencies` set to `on`

Confirm that the state PVC exists. KubeVirt names it after the VM:

[source,bash,role=execute]
----
oc get pvc -n windows-vbs
----

.Expected output
[source,text]
----
NAME                              STATUS   VOLUME     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
persistent-state-for-win2k22-vbs  Bound    pvc-a1b2   10Mi       RWO            nfs-storage    7m
win2k22-vbs-rootdisk              Bound    pvc-c3d4   80Gi       RWO            nfs-storage    7m
----

== Step 5: Enable VBS in the Guest

Take a snapshot first. HVCI refuses to load kernel drivers that do not meet its signing rules, and an incompatible driver leaves the guest in a boot loop:

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: snapshot.kubevirt.io/v1beta1
kind: VirtualMachineSnapshot
metadata:
  name: win2k22-vbs-pre-vbs
  namespace: windows-vbs
spec:
  source:
    apiGroup: kubevirt.io
    kind: VirtualMachine
    name: win2k22-vbs
EOF
----

Windows Server 2022 ships with VBS available but disabled. Open a console session:

[source,bash,role=execute]
----
virtctl vnc win2k22-vbs -n windows-vbs
----

For RDP instead, see xref:remote-access-windows-vms.adoc[Accessing Your Windows VM via Remote Desktop].

Log in as an administrator and open PowerShell as administrator. First confirm the platform requirements are visible to the guest:

[source,powershell]
----
Confirm-SecureBootUEFI
Get-Tpm | Format-List TpmPresent, TpmReady, TpmEnabled
----

.Expected output
[source,text]
----
True

TpmPresent : True
TpmReady   : True
TpmEnabled : True
----

The next three commands are also available as a single script: xref:attachment$windows-vbs-credential-guard/enable-vbs.ps1[Download enable-vbs.ps1].

Enable VBS and require Secure Boot as the platform security feature:

[source,powershell]
----
$dg = 'HKLM:\SYSTEM\CurrentControlSet\Control\DeviceGuard'
New-Item -Path $dg -Force | Out-Null
New-ItemProperty -Path $dg -Name EnableVirtualizationBasedSecurity -Value 1 -PropertyType DWord -Force | Out-Null
New-ItemProperty -Path $dg -Name RequirePlatformSecurityFeatures -Value 1 -PropertyType DWord -Force | Out-Null
----

IMPORTANT: Set `RequirePlatformSecurityFeatures` to `1`, which means Secure Boot only. The value `3` also requires DMA protection, which depends on an IOMMU that KubeVirt VMs do not expose to the guest. With `3`, VBS stays configured but never starts.

Enable HVCI:

[source,powershell]
----
$hvci = 'HKLM:\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity'
New-Item -Path $hvci -Force | Out-Null
New-ItemProperty -Path $hvci -Name Enabled -Value 1 -PropertyType DWord -Force | Out-Null
New-ItemProperty -Path $hvci -Name Locked -Value 0 -PropertyType DWord -Force | Out-Null
----

Enable Credential Guard:

[source,powershell]
----
$lsa = 'HKLM:\SYSTEM\CurrentControlSet\Control\Lsa'
New-ItemProperty -Path $lsa -Name LsaCfgFlags -Value 2 -PropertyType DWord -Force | Out-Null
----

`LsaCfgFlags` accepts `0` for disabled, `1` for enabled with a UEFI lock, and `2` for enabled without a UEFI lock. A UEFI lock writes a firmware variable that survives a registry rollback, so turning Credential Guard off later requires a signed Microsoft tool and physical presence at the firmware. Use `2` in a lab.

TIP: In a domain, deliver the same settings through the Group Policy path *Computer Configuration* > *Administrative Templates* > *System* > *Device Guard* > *Turn On Virtualization Based Security*.

Confirm that the hypervisor is set to launch at boot:

[source,powershell]
----
bcdedit /enum "{current}" | Select-String hypervisorlaunchtype
----

.Expected output
[source,text]
----
hypervisorlaunchtype    Auto
----

If the setting is missing or shows `Off`, set it:

[source,powershell]
----
bcdedit /set hypervisorlaunchtype auto
----

Restart the guest so the secure kernel loads:

[source,powershell]
----
Restart-Computer -Force
----

== Step 6: Verify VBS Is Running

After the guest is back, open PowerShell as administrator and query the Device Guard WMI class:

[source,powershell]
----
Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard |
  Select-Object VirtualizationBasedSecurityStatus, SecurityServicesConfigured,
    SecurityServicesRunning, AvailableSecurityProperties, RequiredSecurityProperties |
  Format-List
----

.Expected output
[source,text]
----
VirtualizationBasedSecurityStatus : 2
SecurityServicesConfigured        : {1, 2}
SecurityServicesRunning           : {1, 2}
AvailableSecurityProperties       : {1, 2, 5}
RequiredSecurityProperties        : {1, 2}
----

Read the values with this table:

[cols="1,1,2",options="header"]
|===
|Property |Value |Meaning

|`VirtualizationBasedSecurityStatus`
|0, 1, 2
|Not enabled, enabled but not running, running

|`SecurityServicesConfigured` and `SecurityServicesRunning`
|1
|Credential Guard

|`SecurityServicesConfigured` and `SecurityServicesRunning`
|2
|HVCI, also called Memory integrity

|`AvailableSecurityProperties`
|1
|Hypervisor support is present

|`AvailableSecurityProperties`
|2
|Secure Boot is present

|`AvailableSecurityProperties`
|3
|DMA protection is present, normally absent in a VM

|`AvailableSecurityProperties`
|5
|NX protections are present

|`AvailableSecurityProperties`
|7
|Mode-Based Execution Control is present
|===

`SecurityServicesRunning` containing both `1` and `2` means Credential Guard and HVCI are active. The exact `AvailableSecurityProperties` list depends on the host CPU and on which features KVM passes through.

As a quick secondary check, confirm that the isolated LSA process is running. Microsoft treats the `Win32_DeviceGuard` query above as the authoritative source, so use this only as a spot check:

[source,powershell]
----
Get-Process -Name LsaIso | Format-List ProcessName, Id
----

.Expected output
[source,text]
----
ProcessName : LsaIso
Id          : 536
----

A `Cannot find a process with the name "LsaIso"` error means Credential Guard is not running.

For the graphical view, run `msinfo32` and read the *System Summary* page. The relevant rows are:

* *Virtualization-based security*: `Running`
* *Virtualization-based security Services Configured*: `Credential Guard, Hypervisor enforced Code Integrity`
* *Virtualization-based security Services Running*: `Credential Guard, Hypervisor enforced Code Integrity`
* *Secure Boot State*: `On`
* *A hypervisor has been detected. Features required for Hyper-V will not be displayed.*

The last line confirms that the guest hypervisor started, which is the part that depends on nested virtualization.

== Limitations and Known Issues

* **No live migration.** Both `host-passthrough` and the required `vmx` feature tie the VM to its node. Node maintenance means shutting the VM down, which is why the manifest sets `evictionStrategy: None`.
* **No production support.** Red Hat supports nested virtualization for development and testing only, so a VBS-enabled Windows VM on OpenShift Virtualization is a test configuration.
* **Performance cost.** VBS adds a hypervisor layer inside a guest that already runs on a hypervisor. Kernel-mode heavy and I/O heavy workloads see the largest drop. Benchmark before you commit to a sizing.
* **Mode-Based Execution Control.** Without hardware MBEC, available on Intel Kaby Lake and later and on recent AMD EPYC processors, HVCI falls back to a slower emulation path. Check for value `7` in `AvailableSecurityProperties`.
* **No DMA protection.** KubeVirt VMs have no vIOMMU, so the DMA protection property is unavailable and `RequirePlatformSecurityFeatures` must stay at `1`.
* **State PVC is part of the VM's identity.** Deleting the `persistent-state-for-<vm-name>` PVC discards the vTPM contents. Credential Guard re-keys itself, but anything sealed to the vTPM, such as BitLocker volumes, becomes unrecoverable without the recovery key. Export BitLocker recovery keys before you clone, restore, or move the VM.
* **Restoring into a different VM is not supported.** KubeVirt supports online and offline snapshots of a VM with persistent state, but restoring such a snapshot into a different VM, which is how VM cloning works, is not supported.
* **A vTPM is not a physical TPM.** The emulated device gives Windows the interface VBS requires, and its state lives in a PVC that a cluster administrator can read. It does not provide the hardware protection of a discrete TPM chip.
* **Credential Guard breaks legacy authentication.** NTLMv1, unconstrained Kerberos delegation, CredSSP credential delegation, and DES or RC4 Kerberos encryption stop working. RDP connections that rely on saved credentials through CredSSP delegation fail after Credential Guard starts.
* **Credential Guard is not supported on domain controllers.** Enable it on member servers and clients only.
* **HVCI requires compatible drivers.** Every kernel driver must pass the stricter code-integrity rules. Use the WHQL-signed VirtIO drivers from the certified `virtio-win` build, see xref:windows-vm-virtio-drivers.adoc[Deploying Windows VMs with VirtIO Drivers]. Test-signed drivers do not load once HVCI is active.
* **Snapshot before you enable HVCI.** An incompatible driver produces a boot loop that is far easier to undo from a snapshot than from Windows recovery, see xref:vm-lifecycle:vm-snapshots.adoc[Creating and Managing VM Snapshots].

== Troubleshooting

=== VM Fails to Start with a Secure Boot Error

KubeVirt rejects a VM that requests Secure Boot without SMM. The API server returns the error at apply time, or the VMI reports it in its conditions:

[source,bash,role=execute]
----
oc describe vmi win2k22-vbs -n windows-vbs
----

Look for a message stating that Secure Boot requires SMM. Add the SMM feature:

[source,yaml]
----
spec:
  template:
    spec:
      domain:
        features:
          smm:
            enabled: true
----

=== VM Stays in Scheduling

A `vmx` feature with `policy: require` adds the node selector `cpu-feature.node.kubevirt.io/vmx` to the `virt-launcher` pod. If no node carries that label, the pod stays pending:

[source,bash,role=execute]
----
oc get pod -n windows-vbs -l vm.kubevirt.io/name=win2k22-vbs
oc describe vmi win2k22-vbs -n windows-vbs
----

An event reading `node(s) didn't match Pod's node affinity/selector` points at a missing label. Return to Step 1 and enable nested virtualization on the nodes.

=== VM Fails Because Persistent State Has No Storage Class

A VM that requests `tpm.persistent` or `efi.persistent` without `spec.storage.vmStateStorageClass` in the `HyperConverged` custom resource fails before the pod starts:

[source,bash,role=execute]
----
oc get vm win2k22-vbs -n windows-vbs -o jsonpath='{.status.printableStatus}{"\n"}'
oc describe vm win2k22-vbs -n windows-vbs
----

The message names the missing VM state storage class. Apply the patch from Step 2.

=== VBS Is Enabled but Not Running

`VirtualizationBasedSecurityStatus` of `1` means Windows accepted the configuration but the secure kernel never started. Work through these causes:

. The guest has no hypervisor support. Run `msinfo32` and check whether the *A hypervisor has been detected* line is present. If it is missing, the `vmx` feature did not reach the guest. Verify it in the domain XML from Step 4.
. The boot entry disables the hypervisor. Run the `bcdedit` command from Step 5 and set `hypervisorlaunchtype` to `auto`.
. The CPU model hides the nested sub-features. Set `domain.cpu.model` to `host-passthrough`.
. A required platform feature is missing. Compare `RequiredSecurityProperties` with `AvailableSecurityProperties`. A required value that is not available, usually `3` for DMA protection, keeps VBS from starting. Set `RequirePlatformSecurityFeatures` to `1`.

=== Credential Guard Is Configured but Not Running

If `SecurityServicesConfigured` contains `1` while `SecurityServicesRunning` does not, VBS itself is the blocker in most cases. Check `VirtualizationBasedSecurityStatus` first and follow the previous section. If VBS is running, confirm Secure Boot and the vTPM in the guest:

[source,powershell]
----
Confirm-SecureBootUEFI
Get-Tpm | Select-Object TpmPresent, TpmReady
----

The `WinInit` source in the system event log states why Credential Guard did not launch:

[source,powershell]
----
Get-WinEvent -FilterHashtable @{LogName='System'; ProviderName='Microsoft-Windows-Wininit'} -MaxEvents 10 |
  Format-List TimeCreated, Id, Message
----

Event ID `13` reports that Credential Guard started. Event ID `15` reports that Credential Guard is configured but the secure kernel is not running, which points back to the VBS section above. Event ID `16` reports a launch failure with an error code.

A `False` from `Confirm-SecureBootUEFI` means the VM booted without Secure Boot. Check that `firmware.bootloader.efi.secureBoot` is `true` and that the guest was installed in UEFI mode, because a guest installed with a BIOS partition layout does not boot with Secure Boot enabled.

=== Secure Boot Settings Reset After Every Reboot

Without `firmware.bootloader.efi.persistent`, OVMF starts from a fresh variable store on each boot and UEFI state is lost. Confirm the setting and the backing PVC:

[source,bash,role=execute]
----
oc get vm win2k22-vbs -n windows-vbs -o jsonpath='{.spec.template.spec.domain.firmware.bootloader.efi}{"\n"}'
oc get pvc persistent-state-for-win2k22-vbs -n windows-vbs
----

=== Get-Tpm Returns No TPM

If the guest reports no TPM, the device is missing from the domain. Check the VM spec:

[source,bash,role=execute]
----
oc get vm win2k22-vbs -n windows-vbs -o jsonpath='{.spec.template.spec.domain.devices.tpm}{"\n"}'
----

An explicit `domain.devices` block overrides `preferredTPM` from a preference, so a VM that mixes a preference with an inline device list must declare the TPM itself.

=== Windows Fails to Boot After Enabling HVCI

A driver that is not HVCI compatible can produce a blue screen loop. Restore the snapshot you took before Step 5. Without a snapshot, boot the Windows Recovery Environment from an installation ISO, load the `SYSTEM` hive, and set `Enabled` to `0` under the `HypervisorEnforcedCodeIntegrity` key. Then identify the driver:

[source,powershell]
----
Get-WinEvent -LogName Microsoft-Windows-CodeIntegrity/Operational -MaxEvents 20 |
  Format-List TimeCreated, Message
----

== Cleanup

Delete the VM. The root disk and the VM state PVC are removed with it:

[source,bash,role=execute]
----
oc delete vm win2k22-vbs -n windows-vbs
----

Delete the project:

[source,bash,role=execute]
----
oc delete project windows-vbs
----

If you set the VM state storage class only for this tutorial, remove it:

[source,bash,role=execute]
----
